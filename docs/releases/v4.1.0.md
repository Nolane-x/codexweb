## Highlights

### Mission Control 4.1

The desktop app now uses one Mission Control shell for Overview, ChatGPT, Agents, Work, Memory, Executions, Connections, Diagnostics, and Settings. Legacy overlapping Council panels are no longer mounted as competing navigation authorities.

Managed ChatGPT conversations are durable documents rather than disposable browser tabs. A saved/parked agent can reacquire its controller-owned conversation without the renderer receiving the private conversation URL and without submitting a new message as a side effect of navigation.

### Execution Control Plane

Every managed browser action can be represented by a typed `CouncilExecutionRun` with:

- stable run identity;
- execution phase;
- Deep State telemetry;
- bounded event history;
- explicit retry-safety classification;
- failure family;
- cancellation authority;
- immutable accepted/rejected command receipts.

BrowserTransport, MCP, owner HTTP, Electron IPC, and Mission Control project the same `CouncilExecutionControlPlane` authority. There is no renderer-owned second execution clock.

### Deep State Engine

Council 4.1 distinguishes meaningful ChatGPT lifecycle conditions including:

- submitted / queued;
- thinking / deep-thinking;
- streaming;
- tool-running;
- waiting-user;
- completing / completed;
- rate-limited;
- conversation-limited;
- connection-lost;
- stalled;
- failed;
- DOM drift.

Deep thinking with live liveness evidence is not treated as a stall. Completion requires stable completion evidence instead of a naive text-stability timeout. DOM drift and ambiguous external-submission outcomes fail closed.

### Submission-boundary safety

`submit-started` is the mechanical retry boundary.

- Before the boundary, a private replay capability can be consumed once when the retry classifier says the operation is safe.
- At or after the boundary, ordinary retry is forbidden.
- Ambiguous post-submit work becomes `uncertain` / operator-resolution-required rather than being automatically replayed.
- Cancellation after submission never claims that ChatGPT definitely did not receive the request unless non-delivery is proven.

### MCP 1.8

Council MCP remains additive-compatible and adds focused execution operations:

- `council_execution_list`
- `council_execution_read`
- `council_execution_events`
- `council_execution_receipts`
- `council_execution_cancel`
- `council_execution_focus`
- `council_execution_capture`
- `council_execution_retry`

The execution facade does not expose conversation URLs, prompts, cookies, tokens, checkpoints, raw DOM selectors, arbitrary JavaScript, screenshot bytes, or hidden chain-of-thought.

### Trusted Electron operator boundary

Electron main owns the loopback owner bearer. The preload/renderer API receives only typed public execution models and opaque run/agent identifiers.

The renderer can list/read execution state, inspect bounded events and receipts, and request bounded cancel/focus/capture/retry operations. URL/script/selector/prompt smuggling is rejected by strict owner-route payload validation.

### Connection truth and optional connector

Tunnel, Council runtime, MCP server, ChatGPT connector, Playwright control, and ChatGPT session are separate connection layers. The UI no longer infers that all layers are healthy because one tunnel or MCP credential exists.

The ChatGPT connector named `CodexWeb Council` is optional for the normal Electron + Playwright browser path. If it is unavailable, Council can continue in browser-only mode instead of failing before every managed prompt.

### DecisionGate v2

When another participant has actually joined the work, a managed final decision now requires independent critique in the latest proposal thread. Self-replies or critique attached only to an obsolete proposal do not satisfy the gate.
